# Counting sort

## Intent
Sort integers, or records by an integer key, without comparing items: count how many items have each key, turn the counts into start positions with a running sum, then place each item at its key's next free position. Taking items in input order makes the sort stable.

## Use when / avoid when
- Use it when keys are integers from a small known range: grades, ages, byte values, day numbers, small enums mapped to integers.
- Use it as the stable inner pass of a radix sort, or alone when the range is not much larger than the number of items.
- Avoid it when the range is far larger than n: it allocates one counter per key value, so this module refuses a range wider than `maxCountingSpan` (2^24) with `ceRangeTooLarge`. Use `merge_sort` or `radix_sort`.
- Avoid it for keys that are not integers (strings, floats): map them to integers first or use a comparison sort.
- Prefer `insertion_sort` for a few dozen items, where the setup cost of counters is not worth it.

## Nim shape
`countingSortByRange(xs, lo, hi, key)` sorts by `key(x)` in `lo .. hi` and returns `Result[seq[T], CountingError]`; negative keys work because each key is offset by `lo`. `countingSortRange` is the integer case, `countingSortAuto` finds the range itself, and `keyHistogram` returns the counts alone. `radix_sort.nim` has `countingSortBy` with a bound `0 ..< k` instead of a range; this module differs by accepting negative keys and by exposing the histogram. Errors (`ceBadRange`, `ceRangeTooLarge`, `ceOutOfRange`) are values, and the range check is written so `hi - lo` cannot overflow.

```nim
import nimcs/fp/result
import nimcs/algo/counting_sort

let temps = @[3, -2, 0, -2, 5, 3]
doAssert countingSortRange(temps, -5, 5) == ok(@[-2, -2, 0, 3, 3, 5], CountingError)
doAssert countingSortAuto(temps) == ok(@[-2, -2, 0, 3, 3, 5], CountingError)

let h = keyHistogram(temps, -2, 5)           # entry i counts the key -2 + i
doAssert h == ok(@[2, 0, 1, 0, 0, 2, 0, 1], CountingError)

let cards = @[(2, "b"), (-1, "x"), (2, "a")]
let byRank = countingSortByRange(cards, -1, 2,
    proc(c: (int, string)): int {.noSideEffect, raises: [].} = c[0])
doAssert byRank == ok(@[(-1, "x"), (2, "b"), (2, "a")], CountingError)   # "b" stays before "a"
```

another module (`Option`, `Result`, `Graph`) needs that module's import too, as in the example
above. A field marked `*` is readable outside the module; a type shown without fields is opaque,
built and read only through the functions.

```text
const maxCountingSpan = 16777216
type CountingError = enum
  ceBadRange,               ## lo is above hi
  ceRangeTooLarge,          ## the range holds more than `maxCountingSpan` values
  ceOutOfRange               ## a key outside lo .. hi
func keyHistogram(keys: openArray[int]; lo, hi: int): Result[seq[int], CountingError]
func countingSortByRange[T](xs: openArray[T]; lo, hi: int; key: proc (x: T): int {.noSideEffect, raises: [].}): Result[seq[T], CountingError]
func countingSortRange(xs: openArray[int]; lo, hi: int): Result[seq[int], CountingError]
func countingSortAuto(xs: openArray[int]): Result[seq[int], CountingError]
```

## Laws and invariants
- For integers inside the range the result equals the standard library's `sorted`, also for a range wider than the data, a single-value range and the empty input (SORT-COUNTING-01).
- Stable: records with equal keys keep their input order (SORT-COUNTING-02).
- A key outside the range gives `ceOutOfRange` (SORT-COUNTING-03).
- A reversed range gives `ceBadRange`, a range wider than `maxCountingSpan` gives `ceRangeTooLarge`, and the widest allowed range is accepted (SORT-COUNTING-04).
- `keyHistogram` entry i is the number of keys equal to `lo + i`, and the entries add up to the number of keys (SORT-COUNTING-05).
- `countingSortAuto` equals `sorted` when the spread is small, and refuses a larger one; the empty input gives an empty result (SORT-COUNTING-06).
- Idempotent: sorting the result again changes nothing (SORT-COUNTING-07).
- For non-negative integers it agrees with `radixSort` (SORT-COUNTING-08).

## Complexity
| Operation | Time | Space |
|---|---|---|
| `countingSortByRange`, n items, range r = hi - lo + 1 | O(n + r) | O(n + r) |
| `keyHistogram` | O(n + r) | O(r) |
| `countingSortAuto` | O(n + r) with r the spread of the data | O(n + r) |

It beats the O(n log n) lower bound for comparison sorts only because it reads the key as an array index.

## Pitfalls
Placing items by walking the input from the last to the first without reversing the positions, or walking forward with positions that count from the end, breaks stability: equal keys come out reversed, and a radix sort built on it sorts wrongly.

```nim bad
for x in xs:                           # walks forward ...
  dec ends[key(x)]                     # ... but fills from the end of the key's block
  placed[ends[key(x)]] = x             # equal keys now come out in reverse order
```

Fill each key's block from its start while walking the input forward (or fill from the end while walking backward). The tests check the order of equal keys against a stable reference.

```nim
import nimcs/fp/result
import nimcs/algo/counting_sort

let pairs = @[(1, "first"), (1, "second"), (0, "zero")]
let sorted = countingSortByRange(pairs, 0, 1,
    proc(p: (int, string)): int {.noSideEffect, raises: [].} = p[0])
doAssert sorted == ok(@[(0, "zero"), (1, "first"), (1, "second")], CountingError)
```
