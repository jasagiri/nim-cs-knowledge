# Maximum flow and bipartite matching

## Intent
Find the largest amount that can be pushed from a source to a sink through arcs with capacities. Edmonds-Karp keeps a residual graph and repeatedly augments along a shortest path (fewest arcs); when no path is left, the vertices still reachable from the source form a minimum cut whose capacity equals the flow. A bipartite matching is a max-flow problem with unit capacities.

## Use when / avoid when
- Use it for capacity problems: network throughput, task assignment, project selection, and any "how many disjoint ..." question that turns into unit capacities.
- Use `bipartiteMatching` to pair two sets (workers and jobs) when each may be used once.
- Avoid it when arcs have costs and you want the cheapest flow: that is min-cost flow, not this module.
- Avoid it for huge graphs: Edmonds-Karp is O(V E^2); Dinic or push-relabel are faster but longer.
- For plain reachability or shortest paths use `bfs` or `dijkstra`.

## Nim shape
`maxFlow(g, source, sink)` reads the weight of each arc of a `Graph` as its capacity and returns `Result[FlowSolution, FlowError]`. `FlowSolution` holds the `value`, the `flows` (per ordered pair, ascending), the `sourceSide` of a minimum cut and the `cut` arcs themselves. Parallel arcs add up; an undirected edge gives each direction its full capacity. Failure (bad vertex, equal endpoints, negative capacity) is a value.

```nim
import nimcs/fp/result
import nimcs/algo/graph
import nimcs/algo/max_flow

let g = buildGraph(4, [edge(0, 1, 3), edge(0, 2, 2), edge(1, 3, 2), edge(2, 3, 3), edge(1, 2, 1)],
    gkDirected).value
let solved = maxFlow(g, 0, 3).value
doAssert solved.value == 5
var cutCapacity = 0
for e in solved.cut:
  cutCapacity += e.weight
doAssert cutCapacity == solved.value          # max-flow = min-cut
```

Matching, as an application:

```nim
import nimcs/fp/result
import nimcs/algo/max_flow

# workers 0..2, jobs 0..2; worker 0 can do job 0 or 1, worker 1 only job 0, worker 2 only job 2
let m = bipartiteMatching(3, 3, [(0, 0), (0, 1), (1, 0), (2, 2)])
doAssert m == ok(@[(0, 1), (1, 0), (2, 2)], FlowError)
```

built and read only through the functions.

```text
type FlowError = enum
  feVertexOutOfRange,       ## source, sink or a matching pair names a vertex that does not exist
  feNegativeCapacity,       ## an arc has a negative capacity
  feSameEndpoints,          ## source and sink are the same vertex
  feNegativeCount            ## a bipartite side has a negative size
type FlowSolution = object
  value*: int                ## the amount of flow from source to sink
  flows*: seq[Edge]          ## per ordered pair (source, target) the flow it carries (weight > 0), ascending
  sourceSide*: seq[int]      ## vertices still reachable from the source in the last residual graph, ascending
  cut*: seq[Edge]            ## the arcs from `sourceSide` to the other vertices: a minimum cut
func maxFlow(g: Graph; source, sink: int): Result[FlowSolution, FlowError]
func bipartiteMatching(leftCount, rightCount: int; pairs: openArray[(int, int)]): Result[seq[(int, int)], FlowError]
```

## Laws and invariants
- The value equals the smallest capacity among all vertex sets that hold the source and not the sink (max-flow min-cut), checked by enumeration on small graphs, and a textbook network gives its known value (GRAPH-MAXFLOW-01).
- The returned cut holds the source, not the sink, and has exactly the flow's value as capacity (GRAPH-MAXFLOW-02).
- The flow respects every capacity and conserves flow at every vertex except source and sink (GRAPH-MAXFLOW-03).
- A bad vertex, equal endpoints and a negative capacity each give their own error (GRAPH-MAXFLOW-04).
- An unreachable sink gives flow zero, and `sourceSide` is what the source reaches (GRAPH-MAXFLOW-05).
- Parallel arcs add up; an opposite arc does not raise the flow (GRAPH-MAXFLOW-06).
- The matching size equals an exhaustive search on small cases (GRAPH-MATCHING-01).
- Every matched pair was offered and no vertex repeats (GRAPH-MATCHING-02).
- A negative count or a pair outside the sides is an error (GRAPH-MATCHING-03).
- Augmenting paths recover from a bad first choice (GRAPH-MATCHING-04).

## Complexity
| Operation | Time | Space |
|---|---|---|
| `maxFlow` | O(V E^2) worst case (at most V E / 2 augmentations of O(E) each) | O(V + E) |
| `bipartiteMatching`, L left, R right, P pairs | O(min(L, R) * (L + R + P)): the flow is at most min(L, R) and each augmentation is O(L + R + P) | O(L + R + P) |

## Pitfalls
Picking augmenting paths by depth-first search (or by largest capacity) and no reverse arcs: a first choice that blocks a better assignment is never undone, and with depth-first order the number of augmentations can depend on the capacities.

```nim bad
# greedy: send along the first path found and never create reverse arcs
for path in allPathsFromSourceToSink:      # pseudo-code
  let b = bottleneck(path)
  for e in path:
    cap[e] -= b                            # no cap[reverse(e)] += b
```

Always add the amount back on the reverse arc and choose paths by breadth-first search, as `maxFlow` does.

```nim
import nimcs/fp/result
import nimcs/algo/graph
import nimcs/algo/max_flow

# Taking 0 -> 1 -> 2 -> 3 first blocks both outer paths; the reverse arc lets flow be undone.
let g = buildGraph(4, [edge(0, 1, 1), edge(0, 2, 1), edge(1, 2, 1), edge(1, 3, 1), edge(2, 3, 1)],
    gkDirected).value
doAssert maxFlow(g, 0, 3).value.value == 2
```
