# Two pointers and sliding window

## Intent
Replace a nested loop over index pairs by one scan with two indices that each move in one direction only. It works when moving an index can rule out a whole family of candidates at once: in a sorted sequence, a sum that is too small rules out the left element with every remaining partner.

## Use when / avoid when
- Use two pointers from both ends for pair problems on sorted data (pair with a given sum, closest pair, palindrome checks).
- Use a sliding window for the longest or shortest run of consecutive elements under a monotone condition (a sum of non-negative numbers, a count of distinct items) and for aggregates over every fixed-size window.
- Avoid it when the condition is not monotone: with negative numbers a window's sum can fall when it grows, so shrinking from the left proves nothing; use prefix sums with a map or `binary_search` over `prefix_sum`.
- Avoid it on unsorted data for pairs: sort first, or use a hash set, if indices are not needed.

## Nim shape
Three `func`s, all returning `Result` so a broken precondition is a value. `pairWithSum` checks sortedness itself (O(n), same order as the scan). `longestWindowAtMost` needs non-negative elements and bound. `windowSums` keeps a running sum, adding the entering and dropping the leaving element. `Window` is a plain `(start, len)` value, never a slice into the input.

```nim
import nimcs/fp/result
import nimcs/algo/two_pointers

doAssert pairWithSum([1, 3, 4, 6, 9], 10) == ok((0, 4), PairError)
doAssert pairWithSum([1, 2, 4], 100) == err((int, int), peNoPair)
doAssert pairWithSum([3, 1, 2], 4) == err((int, int), peNotSorted)

let w = longestWindowAtMost([1, 2, 1, 1, 5, 1, 1, 1], 3)
doAssert w == ok(Window(start: 5, len: 3), WindowError)
doAssert windowSums([1, 2, 3, 4], 2) == ok(@[3, 5, 7], WindowError)
```

## Public API

Every exported symbol of `src/nimcs/algo/two_pointers.nim`, generated by `nim apiSections` (the
tests fail when it drifts). `import nimcs/algo/two_pointers` brings these names. A type they use from
another module (`Option`, `Result`, `Graph`) needs that module's import too, as in the example
above. A field marked `*` is readable outside the module; a type shown without fields is opaque,
built and read only through the functions.

```text
type PairError = enum
  peNotSorted,              ## the input is not in ascending order, so the method would give wrong answers
  peNoPair                   ## no two elements add up to the target
type Window = object
  start*, len*: int
type WindowError = enum
  weNegativeElement,        ## the window method needs non-negative numbers: a negative one breaks "shrinking never raises the sum"
  weNegativeBound,          ## no window, not even the empty one, has a sum below zero
  weBadSize                  ## a fixed window size below one
func `==`(a, b: Window): bool
func pairWithSum(sortedXs: openArray[int]; target: int): Result[(int, int), PairError]
func longestWindowAtMost(xs: openArray[int]; bound: int): Result[Window, WindowError]
func windowSums(xs: openArray[int]; size: int): Result[seq[int], WindowError]
```

## Laws and invariants
- `pairWithSum` equals a brute-force search over all pairs, taking the smallest first index and, for it, the largest second index (TECH-TWOPTR-01).
- No pair, an empty input and a single element give `peNoPair` (TECH-TWOPTR-02).
- An unsorted input gives `peNotSorted` (TECH-TWOPTR-03).
- `longestWindowAtMost` equals a brute-force search (longest, then earliest) and its sum is within the bound (TECH-WINDOW-01).
- Each of `windowSums` equals the re-added sum of its window (TECH-WINDOW-02).
- A negative element gives `weNegativeElement` (TECH-WINDOW-03); a negative bound gives `weNegativeBound` (TECH-WINDOW-04); a size below one gives `weBadSize` (TECH-WINDOW-05).

## Complexity
| Operation | Time | Space |
|---|---|---|
| `pairWithSum` | O(n): each pointer moves at most n steps in total | O(1) |
| `longestWindowAtMost` | O(n): `left` and `right` each move at most n steps (amortized O(1) per element) | O(1) |
| `windowSums` | O(n) | O(n - size + 1) for the output |

## Pitfalls
Using the sliding window on data with negative numbers: the loop shrinks while the sum is above the bound, but removing a negative element raises the sum, so a longer valid window can be skipped.

```nim bad
func longestUnder(xs: seq[int]; bound: int): int =
  var left, sum = 0
  for right in 0 ..< xs.len:
    sum += xs[right]
    while sum > bound:       # wrong for xs = [5, -4, 1]: the window [5, -4, 1] has sum 2 <= 2
      sum -= xs[left]
      inc left
    result = max(result, right - left + 1)
```

Reject negative input (as `longestWindowAtMost` does with `weNegativeElement`), or switch to prefix sums.

```nim
import nimcs/fp/result
import nimcs/algo/two_pointers

doAssert longestWindowAtMost([5, -4, 1], 2) == err(Window, weNegativeElement)
```
