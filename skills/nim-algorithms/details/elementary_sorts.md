# Selection sort and shellsort

## Intent
Two elementary sorts that show the trade-offs of the simplest ideas. Selection sort puts the smallest remaining element in front with one swap per position. Shellsort runs insertion sort over elements a gap apart, shrinking the gap to 1, so elements travel far in few steps.

## Use when / avoid when
- Use selection sort when writing an element is much costlier than comparing two (it makes at most n - 1 swaps), or to teach "loop invariant: the prefix is final".
- Use shellsort for mid-sized inputs (hundreds to a few thousand elements) when you want no extra memory and no recursion.
- Avoid both when equal elements must keep their input order: neither is stable. Use `insertion_sort` (stable, best for short or nearly sorted input) or `merge_sort` (stable, O(n log n)).
- Avoid selection sort on nearly sorted input: it always makes n(n-1)/2 comparisons, where `insertion_sort` needs about n.
- Avoid both for large inputs: reach for `merge_sort`, `quick_sort` or `heap_sort`.

Stability: `insertion_sort` is stable; `selectionSort` and `shellSort` are not.

## Nim shape
Each sort takes any `openArray[T]` and an optional `less` comparator and returns a new `seq[T]`; the input is untouched. `shellGaps(n)` gives Knuth's gaps (1, 4, 13, 40, ... below n div 3, largest first). `shellSortWithGaps` takes your own gap sequence and returns `Result[seq[T], GapError]`: any strictly descending list of positive gaps ending in 1 sorts correctly, only the speed changes. `selectionSwaps` counts the swaps selection sort makes.

```nim
import nimcs/fp/result
import nimcs/algo/elementary_sorts

let xs = @[5, 2, 9, 1, 5, 6]
doAssert selectionSort(xs) == @[1, 2, 5, 5, 6, 9]
doAssert shellSort(xs) == @[1, 2, 5, 5, 6, 9]
doAssert shellSort(xs, proc(a, b: int): bool {.noSideEffect, raises: [].} = a > b) == @[9, 6, 5, 5, 2, 1]
doAssert shellGaps(1000) == @[121, 40, 13, 4, 1]
doAssert selectionSwaps(xs, proc(a, b: int): bool {.noSideEffect, raises: [].} = a < b) <= xs.len - 1

let less = proc(a, b: int): bool {.noSideEffect, raises: [].} = a < b
doAssert shellSortWithGaps(xs, [3, 1], less) == ok(@[1, 2, 5, 5, 6, 9], GapError)
doAssert shellSortWithGaps(xs, [3, 2], less) == err(seq[int], gapNoFinalOne)
```

## Laws and invariants
- `selectionSort(xs) == sorted(xs)` (ELEMSORT-SELECT-01), and with a descending comparator the result is sorted descending (ELEMSORT-SELECT-02).
- Selection sort makes at most len - 1 swaps, and none on sorted input (ELEMSORT-SELECT-03).
- Selection sort is not stable: `[(2,a), (2,b), (1,c)]` by key comes out `[(1,c), (2,b), (2,a)]`, while `insertionSort` keeps `a` before `b` (ELEMSORT-SELECT-04).
- Idempotent, and an empty or one-element input comes back unchanged (ELEMSORT-SELECT-05).
- `shellSort(xs) == sorted(xs)`, ascending and with a descending comparator, also for a 500-element input that uses five gaps (ELEMSORT-SHELL-01).
- Shellsort with any strictly descending positive gap list ending in 1 sorts correctly (ELEMSORT-SHELL-02).
- Shellsort is not stable, shown on a three-record witness with gaps 2, 1 and on fifteen records with the default gaps (ELEMSORT-SHELL-03).
- The default gaps are Knuth's, strictly descending, below n div 3 except the final 1 (ELEMSORT-SHELL-04).
- An empty list, a gap below one, a non-descending list and a list not ending in 1 each give their own `GapError` (ELEMSORT-SHELL-05).
- Idempotent, and an empty or one-element input comes back unchanged (ELEMSORT-SHELL-06).

## Complexity
| Operation | Time | Space |
|---|---|---|
| `selectionSort` | Theta(n^2) comparisons always, at most n - 1 swaps | O(n) for the result |
| `shellSort` with Knuth's gaps | O(n^(3/2)) worst case; typically much less | O(n) for the result, O(1) extra |
| `insertion_sort` for comparison | O(n^2) worst case, O(n) when nearly sorted | O(n) for the result |

The O(n^(3/2)) bound for Knuth's gaps is a known result; its exact behaviour depends on the gap sequence, which is why `shellSortWithGaps` exists.

## Pitfalls
Sorting by two keys with two passes (first the secondary key, then the primary) relies on the second pass being stable. With an unstable sort the secondary order is lost.

```nim bad
# sort by city, then by age, expecting "by age within each city"
let byAge = selectionSort(people, proc(a, b: Person): bool = a.age < b.age)
let byCity = selectionSort(byAge, proc(a, b: Person): bool = a.city < b.city)   # may scramble ages
```

Compare both keys in one comparator, or use a stable sort for the second pass.

```nim
import nimcs/algo/elementary_sorts
import nimcs/algo/insertion_sort

type Person = object
  city: string
  age: int

let people = @[Person(city: "b", age: 30), Person(city: "a", age: 40), Person(city: "a", age: 20)]
let byAge = insertionSort(people, proc(a, b: Person): bool {.noSideEffect, raises: [].} = a.age < b.age)
let byCity = insertionSort(byAge, proc(a, b: Person): bool {.noSideEffect, raises: [].} = a.city < b.city)
doAssert byCity[0].age == 20 and byCity[1].age == 40       # ages stay ordered inside "a"

let oneComparator = shellSort(people, proc(a, b: Person): bool {.noSideEffect, raises: [].} =
  if a.city != b.city: a.city < b.city else: a.age < b.age)
doAssert oneComparator == byCity
```
