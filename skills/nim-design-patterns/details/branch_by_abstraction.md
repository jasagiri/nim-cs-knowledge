# Branch by abstraction

## Intent
Replace an implementation inside the trunk, behind an interface, in small steps, instead of on a long-lived branch. First the callers are moved behind an abstraction that the old implementation fills. Then the new implementation is written behind the same abstraction. A stage value says which one answers: old, shadow (the old answers while both run and a mismatch is reported) or new. The callers do not change when the stage does.

## Use when / avoid when
- Use when a replacement takes many commits, other work must keep landing on the trunk, and the replacement cannot be reached from outside by a route table.
- Use when you want evidence that the new implementation agrees with the old one on real inputs before it answers.
- Avoid when the replacement fits in one commit.
- Avoid when the two implementations cannot both run: the shadow stage needs it, so without it the stage collapses to a switch.
- Remove the losing side when the stage reaches new for good; an abstraction with one implementation and a dead switch is clutter.

## Nim shape
`src/nimcs/patterns/branch_by_abstraction.nim`. `Pricing` is the abstraction, a record of one proc with its contract in the doc comment. `oldPricing` and `newPricing` satisfy the contract in two ways; `uncheckedPricing` is a replacement that forgot a clamp. `invoiceTotal` is a caller and knows only `Pricing`. `select` picks the implementation that answers at a stage, `compare` finds a mismatch, `invoiceAt` answers at a stage and reports the mismatch only while the stage is shadow, and `advance` and `retreat` move the stage.

```nim
import std/options
import nimcs/patterns/branch_by_abstraction

let items = @[1000, -50, 500]
doAssert invoiceTotal(oldPricing(), items, 10) == 1650
doAssert invoiceTotal(newPricing(), items, 10) == 1650

# Shadow: the old answer is returned, and the rewrite that forgot the clamp is caught.
let shadow = invoiceAt(stShadow, oldPricing(), uncheckedPricing(), items, 10)
doAssert shadow.total == 1650
doAssert shadow.mismatch == some(Mismatch(oldTotal: 1500, newTotal: 1450))

let stage = advance(advance(stOld))
doAssert stage == stNew and retreat(stage) == stShadow
```

## Public API

Every exported symbol of `src/nimcs/patterns/branch_by_abstraction.nim`, generated by `nim apiSections` (the
tests fail when it drifts). `import nimcs/patterns/branch_by_abstraction` brings these names. A type they use from
another module (`Option`, `Result`, `Graph`) needs that module's import too, as in the example
above. A field marked `*` is readable outside the module; a type shown without fields is opaque,
built and read only through the functions.

```text
type Stage = enum
  stOld, stShadow, stNew
type Pricing = object
  subtotal*: proc (cents: seq[int]): int {.noSideEffect, raises: [].}
type Mismatch = object
  oldTotal*, newTotal*: int
type Answer = tuple[total: int, mismatch: Option[Mismatch]]
func oldPricing(): Pricing
func newPricing(): Pricing
func uncheckedPricing(): Pricing
func invoiceTotal(p: Pricing; cents: seq[int]; taxPercent: int): int
func select(stage: Stage; old, replacement: Pricing): Pricing
func compare(old, replacement: Pricing; cents: seq[int]): Option[Mismatch]
func invoiceAt(stage: Stage; old, replacement: Pricing; cents: seq[int]; taxPercent: int): Answer
func advance(s: Stage): Stage
func retreat(s: Stage): Stage
```

## Laws and invariants
Why this is testable: the implementations are values of one record type and the stage is an enum, so "the caller cannot tell" is an equation between totals.
- Two implementations of one contract give the caller the same total at every stage (PAT-BRANCHBYABSTRACTION-01).
- At the shadow stage the answer is the old one, and a mismatch is reported exactly when the two differ (PAT-BRANCHBYABSTRACTION-02).
- At the new stage the answer is the new implementation's whatever the old returns; at the old stage it is the old one's (PAT-BRANCHBYABSTRACTION-03).
- `advance` and `retreat` move one step and stop at the ends (PAT-BRANCHBYABSTRACTION-04).

## Complexity
The shadow stage runs both implementations, so it costs the sum of the two. The other stages cost one.

## Pitfalls
The abstraction is easy to shape after the old implementation, and then the new one cannot fit it. Write down the contract (here: negative lines count as 0) before the second implementation, and test both against it.

```nim bad
func invoiceTotal(cents: seq[int]; taxPercent: int): int =
  let sub = oldSubtotal(cents)          # the caller names the old implementation
  sub + sub * taxPercent div 100
```

Hand the caller the abstraction, so the stage can change without touching it:

```nim
import nimcs/patterns/branch_by_abstraction

doAssert invoiceTotal(select(stNew, oldPricing(), newPricing()), @[100], 0) == 100
```

A mismatch in the shadow stage is a finding, not a failure of the stage: fix the replacement or the contract, then run the stage again.
