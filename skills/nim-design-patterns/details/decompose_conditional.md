# Decompose conditional

## Intent
A condition that mixes several ideas in one expression (an age, a weekday, an hour, a flag) is understood only by running it in your head, and a change to one clause can silently change the precedence of another. Decomposing it gives each idea a named predicate, gives the outcome a value type that says which rule applied, and keeps the decision a short list in priority order.

## Use when / avoid when
- Use when a condition has three or more clauses, mixes `and` with `or`, or you cannot say the rule aloud in one sentence.
- Use when someone will ask "why did this case get that result": the tier is the answer, not a trace.
- Avoid when the condition is one comparison; a name for it adds nothing.
- Avoid when the branches are kinds of one tag: that is `replace_conditional_with_polymorphism.md`.

## Nim shape
`src/nimcs/patterns/decompose_conditional.nim`. The price of a museum ticket in yen. `priceBefore` is the single tangled condition. `isChild`, `isSenior`, `isWeekday`, `isDaytimeStudent` and `isEvening` are the named ideas. `tierOf` lists the rules in priority order and returns a `Tier`; `priceOf` turns a tier into money; `price` composes them and is tested equal to `priceBefore` on generated visitors.

```nim
import nimcs/patterns/decompose_conditional

let v = Visitor(age: 70, isStudent: false, weekday: 2, hour: 21)
doAssert v.isSenior and v.isWeekday and v.isEvening
doAssert v.tierOf == tFree           # free beats the reduced rate the evening would give
doAssert v.price == v.priceBefore
doAssert Visitor(age: 30, weekday: 6, hour: 20).tierOf == tReduced
```

## Public API

Every exported symbol of `src/nimcs/patterns/decompose_conditional.nim`, generated by `nim apiSections` (the
tests fail when it drifts). `import nimcs/patterns/decompose_conditional` brings these names. A type they use from
another module (`Option`, `Result`, `Graph`) needs that module's import too, as in the example
above. A field marked `*` is readable outside the module; a type shown without fields is opaque,
built and read only through the functions.

```text
type Visitor = object
  age*: int                  ## whole years
  isStudent*: bool
  weekday*: int              ## 0 = Monday .. 6 = Sunday
  hour*: int                 ## 0 .. 23
type Tier = enum
  tFree, tReduced, tFull
const FullPrice = 1500
const ReducedPrice = 800
func priceBefore(v: Visitor): int
func isChild(v: Visitor): bool
func isSenior(v: Visitor): bool
func isWeekday(v: Visitor): bool
func isDaytimeStudent(v: Visitor): bool
func isEvening(v: Visitor): bool
func tierOf(v: Visitor): Tier
func priceOf(t: Tier): int
func price(v: Visitor): int
```

## Laws and invariants
- The decomposed price equals the tangled price for every visitor (PAT-DECOMPOSECONDITIONAL-01).
- A child and a weekday senior are always free; a daytime student and an evening visitor are never at the full tier; free beats reduced (PAT-DECOMPOSECONDITIONAL-02).
- Each side of each boundary gives the documented tier (PAT-DECOMPOSECONDITIONAL-03).
- The prices of the tiers increase from free to full (PAT-DECOMPOSECONDITIONAL-04).

## Complexity
O(1) per decision; each predicate is a comparison, and the priority list evaluates them left to right with short circuit.

## Pitfalls
The common mistake is to name the clauses but keep the tangle: a long function whose body still mixes the predicates with arithmetic and returns a bare number. The caller still cannot tell which rule fired.

```nim bad
func price(v: Visitor): int =
  if v.isChild or (v.isSenior and v.isWeekday): 0
  elif v.isDaytimeStudent or v.isEvening or v.isSenior: 800
  else: 1500   # the tier is lost and the amounts are repeated elsewhere
```

Return the tier, and map the tier to the amount in one place:

```nim
import nimcs/patterns/decompose_conditional

let t = Visitor(age: 5, weekday: 1, hour: 10).tierOf
doAssert t == tFree and t.priceOf == 0
```

Write the predicates as boundaries (`age < 6`), and test both sides of each boundary, not only the middle.
