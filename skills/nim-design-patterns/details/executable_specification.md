# Executable specification

## Intent
Each fact about a behaviour is written once, in the place a machine checks it. A written specification drifts from the code because nothing fails when the two disagree, so the work is split. The specification states the obligation, one sentence per rule, and its ID is what the tests must cover: that list is decided by people and the implementation cannot grow or shrink it. The values and examples live only in the tests, as a table run against the code. The type carries the rule itself, so a value that breaks it cannot be built. Code says How, tests say What, the commit says Why, a comment says Why not.

## Use when / avoid when
- Use when a rule has a specification that people read and approve, so the specification, the examples and the code cannot say different things.
- Use when a specification row has started to list values ("accepts `a`, `b` and `c`"): move the values to an example table and keep the sentence.
- Use a property test for a rule that holds for every input, and an example table for the cases a person chose (the edges, the errors, the cases that once broke).
- Avoid writing the explanation of the implementation as a document to keep. Generate it from the code when someone needs it, and throw it away.
- Avoid a specification sentence with two level words ("MUST … and MAY …"): it is two rules and needs two IDs.

## Nim shape
`src/nimcs/patterns/executable_specification.nim`. The rule is a release version `vMAJOR.MINOR.PATCH`. `Version` has private fields, so the only ways in are `version` (a `range` per part) and `parseVersion`, which accepts only the form `$` prints; a bad text is a `VersionError` naming the first rule it breaks. `Example` is one row of an example table: a name, an input and the expected output. `failures` runs a table against any function and returns the names of the rows that disagree.

```nim
import nimcs/patterns/executable_specification

# The specification row says only: "A text that is not `v` and three dot-separated parts of
# one to six decimal digits without a leading zero is an error naming the first rule it breaks."
# The values are here, once.
let table: seq[Example[string, Result[Version, VersionError]]] = @[
  (name: "no v", input: "1.2.3", expected: err(Version, veShape)),
  (name: "leading zero", input: "v1.02.3", expected: err(Version, veLeadingZero)),
  (name: "seven digits", input: "v1.2.1000000", expected: err(Version, veTooLarge)),
  (name: "accepted", input: "v1.10.0", expected: ok(version(1, 10, 0), VersionError))]
doAssert failures(table, parseVersion).len == 0

# The type carries the rule: a parsed version prints back to its text, and orders by number.
let v = parseVersion("v1.10.0").value
doAssert $v == "v1.10.0"
doAssert version(1, 9, 9) < v
```

## Public API

Every exported symbol of `src/nimcs/patterns/executable_specification.nim`, generated by `nim apiSections` (the
tests fail when it drifts). `import nimcs/patterns/executable_specification` brings these names. A type they use from
another module (`Option`, `Result`, `Graph`) needs that module's import too, as in the example
above. A field marked `*` is readable outside the module; a type shown without fields is opaque,
built and read only through the functions.

```text
const MaxPart = 999999
type Version = object
type VersionError = enum
  veShape,                  ## not `v` and three parts of decimal digits separated by `.`
  veLeadingZero,            ## a part of two or more digits that starts with `0`
  veTooLarge                 ## a part of more than six digits
type Example[I; O] = tuple[name: string, input: I, expected: O]
func version(major, minor, patch: range[0 .. MaxPart]): Version
func major(v: Version): int
func minor(v: Version): int
func patch(v: Version): int
func parseVersion(text: string): Result[Version, VersionError]
func `$`(v: Version): string
func `<`(a, b: Version): bool
func `<=`(a, b: Version): bool
func failures[I, O](examples: openArray[Example[I, O]]; f: proc (x: I): O {.noSideEffect, raises: [].}): seq[string]
```

## Laws and invariants
Why this is testable: the rule is a pair of inverse functions and an order, so it can be stated over every input, and the chosen cases are data that one routine runs.
- For any version, parsing its printed text gives the same version back (PAT-EXECSPEC-01).
- For any text that parses, printing the parsed version gives that text: only one spelling is accepted (PAT-EXECSPEC-02).
- A bad text is the error the example table names for it (PAT-EXECSPEC-03).
- Versions are ordered as the triples of their parts are, so `v1.10.0` comes after `v1.9.9` (PAT-EXECSPEC-04).
- `failures` names, in table order, exactly the rows the function disagrees with (PAT-EXECSPEC-05).

## Complexity
`parseVersion` is O(length of the text). `failures` calls the function once per row.

## Pitfalls
A specification that lists the values copies the tests, and the copy goes stale first. Here the row names the cases, and a later change to the parser (accepting `v1.2`) updates the test but not the row.

```nim bad
# docs/spec: "Rejects `1.2.3`, `v1.2`, `v1.02.3` and `v1.2.1000000`; accepts `v0.0.0` and `v999999.0.1`."
# tests:     the same six texts, written again.
let rejected = ["1.2.3", "v1.2", "v1.02.3", "v1.2.1000000"]
for t in rejected: doAssert parseVersion(t).isErr
```

State the obligation once in the specification, and keep the values only in the table that the test runs:

```nim
import nimcs/patterns/executable_specification

let table: seq[Example[string, Result[Version, VersionError]]] = @[
  (name: "two parts", input: "v1.2", expected: err(Version, veShape)),
  (name: "zero alone", input: "v0.0.0", expected: ok(version(0, 0, 0), VersionError))]
doAssert failures(table, parseVersion).len == 0
```

Also keep the fields private. With public fields, `Version(major: -1)` builds a value the parser would never return, and the laws stop describing every `Version`.
