# Transactional outbox

## Intent
A service that changes its state and then sends a message can stop between the two, and either nobody is told or a message is sent for a change that never happened. The outbox makes the state change and the messages it must cause one value, saved in one transaction. A relay later delivers the pending messages; a message leaves the outbox only when its delivery was reported successful, so each is delivered at least once, and the receiver, keyed by the message id, applies it once.

## Use when / avoid when
- Use whenever a database write must cause a message to another system: events after an order is placed, a cache invalidation after an update.
- Use with `idempotent_command.md` on the receiving side: delivery is at least once, so duplicates will come.
- Avoid it when losing the message is acceptable; sending directly is simpler.
- Avoid it to get exactly-once delivery: the outbox cannot give that; idempotent receiving does.

## Nim shape
`src/nimcs/patterns/transactional_outbox.nim`. `Unit[S]` holds a state `S` and an `Outbox`. `record(unit, newState, messages)` returns one `Unit` with the new state and the messages added; there is no result with one half only. Ids are `producer-n`, assigned by the outbox and never reused. The relay is two pure functions: `nextBatch(outbox, n)` says what to send, and `settle(outbox, results)` returns the outbox with the delivered messages removed.

```nim
import nimcs/patterns/transactional_outbox

let u0 = initUnit(0, initOutbox("orders"))
let u1 = u0.record(1, [("order.placed", "o-17"), ("stock.reserve", "o-17")])
doAssert u1.state == 1 and u1.outbox.len == 2
let batch = u1.outbox.nextBatch(10)
doAssert batch[0].id == "orders-0"
# The first send worked, the second failed: it stays.
let rest = u1.outbox.settle([delivery("orders-0", dsDelivered), delivery("orders-1", dsFailed)])
doAssert rest.pending.len == 1 and rest.pending[0].id == "orders-1"
doAssert rest.settle([delivery("orders-0", dsDelivered)]) == rest   # a repeated report changes nothing
```

The receiver keys its work by the message id. Here the receiver is an `idempotent_command` ledger, so a message sent twice (the acknowledgement was lost) changes the balance once.

```nim
import nimcs/patterns/transactional_outbox
import nimcs/patterns/idempotent_command

let u = initUnit("v1", initOutbox("pay")).record("v2", [("deposit", "5")])
let m = u.outbox.pending[0]
let cmd = Command(key: m.id, kind: ckDeposit, amount: 5)
let first = initLedger().handle(cmd)
let again = first.ledger.handle(cmd)       # the same message delivered again
doAssert first.ledger.balance == 5 and again.ledger.balance == 5
```

## Public API

Every exported symbol of `src/nimcs/patterns/transactional_outbox.nim`, generated by `nim apiSections` (the
tests fail when it drifts). `import nimcs/patterns/transactional_outbox` brings these names. A type they use from
another module (`Option`, `Result`, `Graph`) needs that module's import too, as in the example
above. A field marked `*` is readable outside the module; a type shown without fields is opaque,
built and read only through the functions.

```text
type Message = object
  id*: string                ## `<producer>-<sequence>`; unique for the life of the outbox
  topic*: string
  payload*: string
type Outbox = object
type Unit[S] = object
  state*: S
  outbox*: Outbox
type DeliveryStatus = enum
  dsDelivered, dsFailed
type Delivery = object
  id*: string
  status*: DeliveryStatus
func `==`(a, b: Message): bool
func `==`(a, b: Outbox): bool
func initOutbox(producer: string): Outbox
func pending(o: Outbox): seq[Message]
func len(o: Outbox): int
func nextSequence(o: Outbox): int
func initUnit[S](state: S; outbox: Outbox): Unit[S]
func enqueue(o: Outbox; topic, payload: string): Outbox
func record[S](u: Unit[S]; newState: S; messages: openArray[(string, string)]): Unit[S]

func settle(o: Outbox; results: openArray[Delivery]): Outbox
func delivery(id: string; status: DeliveryStatus): Delivery
```

## Laws and invariants
- `record` produces the new state and the messages together, with sequential unique ids; the old unit is unchanged (PAT-TXOUTBOX-01).
- Messages keep their topic, payload and order (PAT-TXOUTBOX-02).
- `nextBatch` is the oldest messages up to the count and does not change the outbox (PAT-TXOUTBOX-03).
- After `settle`, exactly the undelivered messages remain, in order: at least once (PAT-TXOUTBOX-04).
- `settle` is idempotent, and results with no success change nothing (PAT-TXOUTBOX-05).
- Ids are never reused after deliveries (PAT-TXOUTBOX-06).
- With acknowledgements lost in any pattern, retried rounds deliver every message and an idempotent receiver applies each exactly once; the outbox ends empty (PAT-TXOUTBOX-07).

## Complexity
`enqueue` copies the pending list, O(m) in the pending count m; `record` of k messages is O(k m). `settle` is O(m r) for r results (it looks each id up in the list of delivered ids); `nextBatch` is O(n). For long outboxes keep the pending messages in a persistent queue and the delivered ids in a set.

## Pitfalls
Writing the state and then sending is the failure this pattern exists for, and removing a message before the delivery is confirmed turns at least once into at most once.

```nim bad
proc placeOrder(db: Db, bus: Bus, o: Order) =
  db.save(o)
  bus.publish(OrderPlaced(id: o.id))    # a crash between the two loses the message
```

Record both in one value and store it in one transaction; settle only what was acknowledged:

```nim
import nimcs/patterns/transactional_outbox

let u = initUnit("new", initOutbox("o")).record("placed", [("order.placed", "17")])
let id = u.outbox.pending[0].id
doAssert u.outbox.settle([delivery(id, dsFailed)]) == u.outbox   # not acknowledged: stays
doAssert u.outbox.settle([delivery(id, dsDelivered)]).len == 0
```

Delivery order across retries is not a guarantee: a failed message stays while later ones go out. If order matters, stop the relay at the first failure (send a batch of one) or let the receiver order by the sequence in the id.
