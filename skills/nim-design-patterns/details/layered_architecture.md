# Layered architecture

## Intent
Split a program into layers that depend in one direction only: the rules at the bottom know nothing of the program around them, the application service above them turns text into rules and results into replies, and the shell at the top is the only place with effects. A module may import a layer below it and never one above or beside it. The rules can then be tested without a parser, the service without a terminal, and no import cycle can form.

## Use when / avoid when
- Use when a program has rules, a protocol and effects that change at different rates, or when a test of the rules needs a database or a terminal.
- Use the direction rule as a check in the test suite, not only as a convention: the test reads the import lines.
- Avoid for a script or a single-purpose tool: three files for forty lines is ceremony.
- Avoid a "util" layer that everything imports; it becomes the place where the rules leak out of their layer.

## Nim shape
`src/nimcs/patterns/layered_architecture.nim` is the composition root: it re-exports the layers and keeps `tangledBefore`, the same behaviour as one routine that splits the line, owns the lists and builds each reply. The layers are `layered_architecture/domain.nim` (a task `Board`; `add` and `complete` return a `Result`), `layered_architecture/service.nim` (`parseCommand`, `execute`, `runLine`, `runLines`; all pure) and `layered_architecture/shell.nim` (`runShell`, the one `proc`, with its reader and writer passed in). The test checks that the replies equal `tangledBefore`'s on generated logs and that the import lines point only downward.

```nim
import nimcs/patterns/layered_architecture

let run = emptyBoard().runLines(["add milk", "add eggs", "done 2", "list"])
doAssert run.replies == @["added 1: milk", "added 2: eggs", "done 2", "1 [ ] milk; 2 [x] eggs"]
doAssert run.replies == tangledBefore(["add milk", "add eggs", "done 2", "list"])
doAssert emptyBoard().add("").isErr
```

## Public API

Every exported symbol of `src/nimcs/patterns/layered_architecture.nim`, generated by `nim apiSections` (the
tests fail when it drifts). `import nimcs/patterns/layered_architecture` brings these names. A type they use from
another module (`Option`, `Result`, `Graph`) needs that module's import too, as in the example
above. A field marked `*` is readable outside the module; a type shown without fields is opaque,
built and read only through the functions.

```text
func tangledBefore(lines: openArray[string]): seq[string]
```

## Laws and invariants
- The layered program gives the replies of the tangled routine for every command log (PAT-LAYEREDARCHITECTURE-01).
- Every layer imports only layers below it; the check also reports a synthetic upward or sideways import (PAT-LAYEREDARCHITECTURE-02).
- `complete` is idempotent, an unknown id and an empty title are refused, and the old board is unchanged (PAT-LAYEREDARCHITECTURE-03).
- Running a log in two halves equals running it whole (PAT-LAYEREDARCHITECTURE-04).
- The shell writes the service's replies in order and returns its final board (PAT-LAYEREDARCHITECTURE-05).

## Complexity
The layers add no cost beyond a function call. In this example `runLines` is O(lines times tasks) because `list` renders the whole board.

## Pitfalls
The common mistake is a lower layer that reaches up for one convenient thing, such as the domain importing the service to format an error message. One such import and the domain can no longer be tested alone.

```nim bad
# layered_architecture/domain.nim
import nimcs/patterns/layered_architecture/service   # upward import: the rules now need the parser
```

Let the lower layer return data (`deEmptyTitle`) and let the upper layer decide the words:

```nim
import nimcs/patterns/layered_architecture

let r = emptyBoard().add("")
doAssert r.isErr and r.error == deEmptyTitle
doAssert emptyBoard().runLine("add").replies == @["error: empty title"]
```

Also do not let the shell contain a rule: when you find an `if` about the business in the loop, move it into the service.
