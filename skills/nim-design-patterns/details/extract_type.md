# Extract type

## Intent
Two or more fields that always travel together (an amount and a currency code) appear side by side in every signature, and every caller must remember the rules that tie them: only the same currency adds, only known codes exist, an amount is not negative. Extracting a value type moves those rules into one smart constructor and one set of operations, so a caller cannot build or combine a wrong value without being told.

## Use when / avoid when
- Use when the same group of fields is passed together in three or more places, or a rule mentions them together.
- Use when a bug came from swapping or mixing two values of the same base type.
- Avoid when the fields are independent and merely adjacent; a type would invent a relation that does not exist.
- Avoid a `distinct` alias when the value has two fields; use an `object` with private fields and a smart constructor.

## Nim shape
`src/nimcs/patterns/extract_type.nim`. `addLoose` is the before: two integers and two string codes, returning a pair. `Money` is the extracted type: its fields are private, `initMoney(minor, code)` is the only door and returns a `Result`, and `plus` returns a `Result` too, with `meCurrencyMismatch` where the loose code silently returned a number under the first code. For the values the loose code handled correctly the two shapes agree.

```nim
import nimcs/patterns/extract_type

let yen = initMoney(1200, "JPY").value
let more = initMoney(300, "JPY").value
doAssert yen.plus(more).value.minor == 1500
doAssert addLoose(1200, "JPY", 300, "JPY") == (1500, "JPY")
doAssert yen.plus(initMoney(5, "USD").value).error == meCurrencyMismatch
doAssert initMoney(-1, "JPY").error == meNegative
```

## Public API

Every exported symbol of `src/nimcs/patterns/extract_type.nim`, generated by `nim apiSections` (the
tests fail when it drifts). `import nimcs/patterns/extract_type` brings these names. A type they use from
another module (`Option`, `Result`, `Graph`) needs that module's import too, as in the example
above. A field marked `*` is readable outside the module; a type shown without fields is opaque,
built and read only through the functions.

```text
type Currency = enum
  cJpy = "JPY", cUsd = "USD", cEur = "EUR"
type MoneyError = enum
  meUnknownCurrency, meCurrencyMismatch, meNegative
type Money = object
func parseCurrency(code: string): Result[Currency, MoneyError]
func initMoney(minor: int; code: string): Result[Money, MoneyError]
func minor(m: Money): int
func currency(m: Money): Currency
func plus(a, b: Money): Result[Money, MoneyError]
func `==`(a, b: Money): bool
func addLoose(aMinor: int; aCode: string; bMinor: int; bCode: string): (int, string)
```

## Laws and invariants
- For one currency, `plus` agrees with the loose addition (PAT-EXTRACTTYPE-01).
- Two currencies that differ are refused, where the loose code answered wrongly (PAT-EXTRACTTYPE-02).
- `initMoney` accepts exactly the known codes with a non-negative amount; an unknown code is reported before a negative amount (PAT-EXTRACTTYPE-03).
- `plus` is commutative and associative and zero is its identity (PAT-EXTRACTTYPE-04).

## Complexity
O(1) per operation; the code lookup is a scan of the three enum values. The value is two machine words.

## Pitfalls
The common mistake is to extract the type but leave its fields public and its constructor open. Then callers build `Money(minor: -5, currency: ...)` directly and the rules are gone again.

```nim bad
type Money = object
  minor*: int          # anyone can set a negative amount
  currency*: string    # and any code
```

Keep the fields private, read them through accessors, and build only through the smart constructor:

```nim
import nimcs/patterns/extract_type

let m = initMoney(100, "EUR").value
doAssert m.minor == 100 and m.currency == cEur
doAssert initMoney(100, "XXX").isErr
```

The one deliberate difference from the old behaviour (mixed currencies) is a change of contract: say so in the commit, since the move is otherwise behaviour-preserving.
