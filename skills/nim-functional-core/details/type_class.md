# Type classes: concepts and generics

## Intent
A type class is "any type that supports these operations". In Nim a plain generic `[T]` is parametric polymorphism (one body for every `T`, which may only move values around), and a generic with a `concept` constraint (`[T: Orderable]`) is a constrained one (the body may use the operations the concept names). An instance is just a type that defines those operations. The compiler checks that the operations exist; whether they obey the laws of the class is yours to test, once per instance.

## Use when / avoid when
- Use a `concept` when one routine must serve several unrelated types (`maxOf` for `int`, `string`, your `Version`).
- Use a plain `[T]` when the routine never looks inside the value (`backwards`, `swap`, `map`): it then works for every type and the compiler rejects any use of an operation `T` is not known to have.
- Avoid a `concept` for a closed set of shapes that you own; an object variant (`adt.md`) is checked for exhaustiveness, a concept is not.
- Avoid expecting a concept to state a law: it can say `(x < y) is bool`, not "`<` is transitive". Put the law in a property test.

## Nim shape

Module: `src/nimcs/fp/type_class.nim`: the `Orderable` concept, routines constrained by it (`maxOf`, `minOf`, `insertSorted`, `isSorted`), the law checker `isTotalOrderOn`, and the unconstrained `backwards`.

```nim
import std/options
import nimcs/fp/type_class

type Version = object
  major, minor: int

func `<`(a, b: Version): bool {.raises: [].} = (a.major, a.minor) < (b.major, b.minor)
func `==`(a, b: Version): bool {.raises: [].} = a.major == b.major and a.minor == b.minor

let versions = @[Version(major: 1, minor: 4), Version(major: 2, minor: 0), Version(major: 1, minor: 9)]
doAssert maxOf(versions).get().major == 2
doAssert maxOf([3, 9, 4]) == some(9)
doAssert maxOf(["pear", "apple"]) == some("pear")
doAssert Version is Orderable
```

Defining the two operators is how a type becomes an instance. Checking the laws of an instance on generated values:

```nim
import nimcs/fp/type_class

type Meters = distinct int
func `<`(a, b: Meters): bool {.borrow.}
func `==`(a, b: Meters): bool {.borrow.}

doAssert isTotalOrderOn(Meters(1), Meters(2), Meters(3))
doAssert not isTotalOrderOn(NaN, 1.0, 2.0)      # float satisfies Orderable but is not totally ordered
```

## Public API

Every exported symbol of `src/nimcs/fp/type_class.nim`, generated by `nim apiSections` (the
tests fail when it drifts). `import nimcs/fp/type_class` brings these names. A type they use from
another module (`Option`, `Result`, `Graph`) needs that module's import too, as in the example
above. A field marked `*` is readable outside the module; a type shown without fields is opaque,
built and read only through the functions.

```text
type Orderable = concept xy
    (x < y) is bool
    (x == y) is bool
func maxOf[T: Orderable](xs: openArray[T]): Option[T]
func minOf[T: Orderable](xs: openArray[T]): Option[T]
func insertSorted[T: Orderable](sortedXs: openArray[T]; x: T): seq[T]
func isSorted[T: Orderable](xs: openArray[T]): bool
func isTotalOrderOn[T: Orderable](a, b, c: T): bool
func backwards[T](xs: openArray[T]): seq[T]
```

## Laws and invariants
- `maxOf` and `minOf` give the last and first element of the sorted sequence, `none` when empty (FP-TYPECLASS-01).
- `insertSorted` keeps a sorted sequence sorted, adds exactly one element, and leaves its input unchanged (FP-TYPECLASS-02).
- `isSorted(xs)` is `xs == sorted(xs)` (FP-TYPECLASS-03).
- `int`, `string`, an object type and a `distinct` type with borrowed operators satisfy the strict-total-order laws on generated triples (FP-TYPECLASS-04).
- The same checker finds the violation in instances that satisfy the concept but break the laws (`<` that ignores part of the value, `float` with `NaN`) (FP-TYPECLASS-05).
- A type is accepted by the concept exactly when it has the operations; a type without them is rejected at the call (FP-TYPECLASS-06).
- A function that never inspects its elements is natural: `backwards(xs.map(g)) == backwards(xs).map(g)` for any `g` (FP-TYPECLASS-07).

## Complexity
Constrained generics are resolved at compile time, one specialised copy per instance type: no dispatch cost at run time, more code. `maxOf`, `minOf`, `isSorted` are O(n); `insertSorted` is O(n) and allocates a new sequence; `isTotalOrderOn` is O(1) per triple.

## Pitfalls
A concept that is satisfied by the shape of the operations says nothing about their meaning. This instance compiles everywhere, but `<` and `==` disagree, so `maxOf` depends on input order:

```nim bad
type Clock = object
  tick: int
func `<`(a, b: Clock): bool = a.tick mod 3 < b.tick mod 3   # ignores most of the value
func `==`(a, b: Clock): bool = a.tick == b.tick              # compares all of it
```

```nim
import nimcs/fp/type_class

type Clock = object
  tick: int

func `<`(a, b: Clock): bool {.raises: [].} = a.tick < b.tick
func `==`(a, b: Clock): bool {.raises: [].} = a.tick == b.tick

doAssert isTotalOrderOn(Clock(tick: 0), Clock(tick: 3), Clock(tick: 6))
```

Order the whole value, or define `==` on the same key. Run `isTotalOrderOn` over many generated triples for each new instance.
