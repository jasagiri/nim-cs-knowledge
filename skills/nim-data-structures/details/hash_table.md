# Hash table (open addressing, linear probing)

## Intent
A hash table maps keys to values in O(1) expected time by turning a key into a slot number. This version keeps every entry in one flat array: a key starts at the slot its hash selects and, if that slot is taken, moves to the next one until it finds its key or an empty slot. The table is a plain value, so an update returns a new table and the old one stays valid.

## Use when / avoid when
- Use it to see how a hash table works, or when you need an immutable snapshot of a lookup table that you build once with `fromPairs` and then only read.
- Use `std/tables` when the table is a local `var` that is updated in a loop: it updates in place, which is allowed because no caller can observe it (ADR-NCK-0002 S5).
- Use `hamt` when old versions must stay cheap: a HAMT updates by copying O(log n) nodes, this table copies the whole slot array.
- Use `rb_tree` when you need keys in order or need a deterministic iteration without sorting.
- Avoid it when the keys have no good `hash` (a weak hash piles entries into one run and lookups degrade to O(n)).

## Nim shape
`HashTable[K, V]` holds a `seq` of slots and a count. A slot is `used`, a key and a value. The capacity is a power of two, so the home slot is `hash(key) and (capacity - 1)`, and the load never exceeds three quarters, so a probe run always ends at an empty slot. Deletion shifts later entries of the run backwards instead of leaving tombstones, so lookups never step over dead slots.

The slot order depends on the hash and on the history of the table, so it is never exposed: `sortedPairs` is the deterministic view (it needs `<` on the key). The key type needs `hash` and `==`.

```nim
import std/options
import nimcs/ds/hash_table

let t = fromPairs([("one", 1), ("two", 2), ("three", 3)])
doAssert t.get("two") == some(2)
doAssert t.get("four").isNone
let u = t.put("four", 4).del("one")
doAssert u.sortedPairs == @[("four", 4), ("three", 3), ("two", 2)]
doAssert t.len == 3                    # t is unchanged
```

Updating a value-typed table in a loop copies the slot array each time, O(n) per step. Build in one pass instead:

```nim
import nimcs/ds/hash_table

func squares(n: int): HashTable[int, int] {.raises: [].} =
  var pairs: seq[(int, int)]           # local mutation, invisible to the caller
  for i in 1 .. n:
    pairs.add (i, i * i)
  fromPairs(pairs)                     # one pass, O(1) amortized per entry

doAssert squares(100).len == 100
doAssert squares(100).invariantsHold
```

## Public API

Every exported symbol of `src/nimcs/ds/hash_table.nim`, generated by `nim apiSections` (the
tests fail when it drifts). `import nimcs/ds/hash_table` brings these names. A type they use from
another module (`Option`, `Result`, `Graph`) needs that module's import too, as in the example
above. A field marked `*` is readable outside the module; a type shown without fields is opaque,
built and read only through the functions.

```text
type HashTable[K; V] = object
func emptyTable[K, V](): HashTable[K, V]
func len[K, V](t: HashTable[K, V]): int
func isEmpty[K, V](t: HashTable[K, V]): bool
func put[K, V](t: HashTable[K, V]; key: K; val: V): HashTable[K, V]
func get[K, V](t: HashTable[K, V]; key: K): Option[V]
func contains[K, V](t: HashTable[K, V]; key: K): bool
func del[K, V](t: HashTable[K, V]; key: K): HashTable[K, V]
func fromPairs[K, V](pairs: openArray[(K, V)]): HashTable[K, V]
func sortedPairs[K, V](t: HashTable[K, V]): seq[(K, V)]
func invariantsHold[K, V](t: HashTable[K, V]): bool
```

## Laws and invariants
- A key put twice holds its latest value and counts once in `len` (DS-HASHTABLE-01).
- An absent key has `get` = `none` and `contains` = false (DS-HASHTABLE-02).
- `del` removes exactly the key; deleting a missing key changes nothing (DS-HASHTABLE-03).
- After any sequence of `put` and `del`, the table holds the same entries as a `std/tables` model (DS-HASHTABLE-04).
- Updates leave the old table unchanged (DS-HASHTABLE-05).
- At every step: the capacity is a power of two, the load is at most 3/4, `count` matches the used slots, and every entry is reachable from its home slot without crossing an empty slot (DS-HASHTABLE-06).
- A thousand keys are all found after growth (DS-HASHTABLE-07).
- `sortedPairs` does not depend on insertion order (DS-HASHTABLE-08).
- With `fromPairs`, the last pair for a repeated key wins (DS-HASHTABLE-09).
- Deleting from the middle of a long probe run keeps the later entries reachable (DS-HASHTABLE-10).

## Complexity
| Operation | Time | Space |
|---|---|---|
| `get`, `contains` | O(1) expected, O(n) worst case (all keys in one run) | O(1) |
| `put`, `del` | O(n): the slot array is copied to keep the old version valid | O(n) |
| `fromPairs` of n pairs | O(n) expected, amortized doubling | O(n) |
| `sortedPairs` | O(n log n) | O(n) |

## Pitfalls
Removing an entry by just emptying its slot cuts the probe run: every later key of that run becomes unreachable, though it is still stored.

```nim bad
type Slot = object
  used: bool
  key, val: int

func removeAt(slots: var seq[Slot]; i: int) =
  slots[i].used = false                # later keys of this run now look absent
```

Close the hole by moving later entries of the run back (`del` does this), or mark a tombstone and skip it while probing. Keep `invariantsHold` in the tests: it checks the no-gap rule directly.

```nim
import std/options
import nimcs/ds/hash_table

let t = fromPairs([(1, 10), (2, 20), (3, 30), (4, 40)])
let d = t.del(2)
doAssert d.invariantsHold
doAssert d.get(3) == some(30) and d.get(4) == some(40)
```

Do not iterate a hash table and use the order in output: it changes with the hash function and the table's history. Sort first (`sortedPairs`).
