# Generational slot map (handles into one owner)

## Intent
Several parts of a program often need to refer to the same thing: a unit, a connection, a node. The shortcut that compiles is a shared `ref` (and a lock or a counter around it), which allocates, hides who owns the value and makes every access pay for the sharing. A slot map keeps every value in one place, a flat `seq` of slots, and gives out a small `Handle` per value: the slot index and the generation the slot had. Other code keeps handles, not values, and asks the owner when it needs one. Removing a value bumps the slot's generation, so a handle to it is rejected even after the slot holds something else.

## Use when / avoid when
- Use it for entities, nodes and resources that are created, destroyed and referred to over time (game units, scene nodes, sessions, timers), when other data needs to point at them.
- Use it when a collection is read and changed in the same pass; the handles stay valid across the deferred changes (see `command_buffer`).
- Use `linked_list` when the order of the elements matters and splicing by handle is the point; the slot map has no order beyond slot order.
- Use `hash_table` when the key is meaningful outside the program (a name, an id from the outside). A handle is only meaningful to the map that issued it.
- Avoid it for a collection that is only appended and scanned: a `seq` is simpler.

## Nim shape
`SlotMap[T]` is a plain value: a `seq` of slots (a live flag, a generation, the element, the next free slot), the head of a free list and a count. The free-list links hold a slot index plus one, so the zero value (`var m: SlotMap[int]`) is the empty map, ready for `insert`. `insert` takes the first free slot or adds one at the end, and returns the map and a `Handle`. `remove` takes the value out, bumps the slot's generation and pushes the slot on the free list. `get`, `contains`, `put` and `remove` check the handle against the slot's live flag and generation, so a stale or unknown handle gives `none`, `false` or the map unchanged.

The updates take the map as `sink` and return it with the result. The caller moves the map in at its last use: write `let r = m.insert(x)` and then `m = r.map`, and the slots are not copied. A failed `remove` or `put` returns the map too, so a map that was moved in is not lost.

```nim
import std/options
import nimcs/ds/slot_map

type Unit = object
  name: string
  hp: int

var units = emptySlotMap[Unit]()
let a = units.insert(Unit(name: "a", hp: 3))
units = a.map                                  # last use of the old map: moved, not copied
let b = units.insert(Unit(name: "b", hp: 5))
units = b.map
doAssert units.len == 2

# Other code keeps handles, not references.
var squad = @[a.handle, b.handle]
doAssert units.get(squad[0]).get.hp == 3

let hit = units.put(b.handle, Unit(name: "b", hp: 4))
units = hit.map
doAssert hit.ok and units.get(b.handle).get.hp == 4

for h, u in units.pairs:                       # live handles and values in slot order
  doAssert units.contains(h) and u.hp > 0
squad.setLen 1
```

A handle to a removed value stays stale, even after its slot is reused:

```nim
import std/options
import nimcs/ds/slot_map

let first = emptySlotMap[string]().insert("old")
let gone = first.map.remove(first.handle)       # the value comes back with the map
doAssert gone.removed == some("old")
let again = gone.map.insert("new")               # reuses the freed slot, generation + 1
doAssert again.handle.index == first.handle.index
doAssert again.handle.generation == first.handle.generation + 1
doAssert again.map.get(first.handle).isNone      # the old handle does not see "new"
doAssert not again.map.put(first.handle, "x").ok
doAssert again.map.get(again.handle) == some("new")
```

## Public API

Every exported symbol of `src/nimcs/ds/slot_map.nim`, generated by `nim apiSections` (the
tests fail when it drifts). `import nimcs/ds/slot_map` brings these names. A type they use from
another module (`Option`, `Result`, `Graph`) needs that module's import too, as in the example
above. A field marked `*` is readable outside the module; a type shown without fields is opaque,
built and read only through the functions.

```text
type Handle = object
  index*: int
  generation*: int
type SlotMap[T] = object
func emptySlotMap[T](): SlotMap[T]
func len[T](m: SlotMap[T]): int
func isEmpty[T](m: SlotMap[T]): bool
func `==`(a, b: Handle): bool
func contains[T](m: SlotMap[T]; h: Handle): bool
func get[T](m: SlotMap[T]; h: Handle): Option[T]
func insert[T](m: sink SlotMap[T]; x: sink T): tuple[map: SlotMap[T], handle: Handle]
func remove[T](m: sink SlotMap[T]; h: Handle): tuple[map: SlotMap[T], removed: Option[T]]
func put[T](m: sink SlotMap[T]; h: Handle; x: sink T): tuple[map: SlotMap[T], ok: bool]
iterator pairs[T](m: SlotMap[T]): tuple[handle: Handle, value: T]
func `==`[T](a, b: SlotMap[T]): bool
func invariantsHold[T](m: SlotMap[T]): bool
```

## Laws and invariants
- The empty map, which is also the zero value `default(SlotMap[T])`, is empty, rejects every handle and takes an insert (DS-SLOTMAP-01).
- Inserting returns a handle whose value is the one inserted, and the other handles keep theirs (DS-SLOTMAP-02).
- Two live handles are never equal (DS-SLOTMAP-03).
- `len` is the number of inserts minus the number of successful removes, and every handle agrees with a model of live handles and values (DS-SLOTMAP-04).
- A removed handle stays stale after its slot is reused, for `get`, `contains`, `remove` and `put` (DS-SLOTMAP-05).
- A stale or unknown handle changes nothing: `remove` and `put` return the map as it was (DS-SLOTMAP-06).
- `put` replaces the value and keeps the handle and the length (DS-SLOTMAP-07).
- Insertion reuses free slots first, the most recently freed first, with the generation bumped (DS-SLOTMAP-08).
- `pairs` yields the live handles in slot order, each with its value (DS-SLOTMAP-09).
- A map the caller still uses is unchanged by an `insert`, `remove` or `put` on it (DS-SLOTMAP-10).
- Count, free list and generations are consistent after every operation (DS-SLOTMAP-11).
- With the map moved in at its last use, `put`, `remove` and an `insert` into a freed slot allocate nothing, whatever the size (DS-SLOTMAP-12).
- Equal histories give equal maps; a different value, handle or free list makes them differ (DS-SLOTMAP-13).

## Complexity
| Operation | Time | Space |
|---|---|---|
| `get`, `contains`, `len`, `isEmpty` | O(1) | O(1) |
| `insert`, `put`, `remove` with the map moved in | O(1); `insert` into a new slot is amortised O(1) for the growth of the `seq` | O(1) extra; no allocation for `put`, `remove` or an `insert` into a freed slot |
| the same when the caller still uses the map it passed in | O(n): the slots are copied once | O(n) |
| `pairs` | O(slots), dead slots included | O(1) |
| `==`, `invariantsHold` | O(slots) | O(1) |

Measured with `-d:nimAllocStats` (tests/test_ds_slot_map.nim): 50 `put`s on maps of 10, 100 and 1000 values, each moved in, allocate nothing; the same 50 `put`s, each on a map the caller keeps reading afterwards, allocate 50 times (one copy of the slots per call). `m = m.put(h, x).map` also copies: the result tuple is a temporary and its field is copied out, so assign the result to a `let` first. A generation is an `int`; wrapping needs 2^63 removals of one slot.

## Pitfalls
Sharing the value with a `ref` makes the compiler quiet and every access pay for it, and nothing says who owns the value or when it is gone.

```nim bad
type
  Unit = ref object
    hp: int
  Squad = object
    members: seq[Unit]
  Target = object
    focus: Unit          # a second owner of the same unit: it outlives the squad's idea of "dead"
```

Keep one owner, and hand out handles. A dead unit's handle is rejected instead of keeping the unit alive.

```nim
import std/options
import nimcs/ds/slot_map

type Unit = object
  hp: int

let u = emptySlotMap[Unit]().insert(Unit(hp: 3))
let focus = u.handle                              # a handle, not a second owner
let gone = u.map.remove(focus)
doAssert gone.removed.isSome
doAssert gone.map.get(focus).isNone               # the target is simply gone
```

Chaining the result of an update and taking its `map` field copies the slots on every call.

```nim bad
for j in 0 ..< 1000:
  m = m.put(hs[j], j).map     # a copy of all slots per call
```

Bind the result and move the map out of it.

```nim
import nimcs/ds/slot_map

var m = emptySlotMap[int]()
var hs: seq[Handle]
for i in 0 ..< 4:
  let r = m.insert(i)
  m = r.map
  hs.add r.handle
for j in 0 ..< 4:
  let r = m.put(hs[j], j * 2)                   # `m` is not used again before it is reassigned
  m = r.map
doAssert m.invariantsHold and m.len == 4
```
